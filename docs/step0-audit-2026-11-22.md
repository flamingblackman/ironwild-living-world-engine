# Step 0 Audit — Ironwild Living World Engine (automation upgrade)

Date: 2026-11-22. No code changed. Everything below was verified against
the code on disk and, where the item asked for numbers, against fresh
simulations: a 400-tick and a 1,000-tick run of a fresh Fork A world
(seeded from `seed/fork-a.internal.json`, one continuous `run_ticks`
call, RNG seeded once from `rng_seed`). Reports:
`runs/audit-step0/report-400.json`, `runs/audit-step0/report-1000.json`;
simulator: `tools/audit_step0.py`.

Verdict shorthand: CONFIRMED (the item holds as written), CORRECTED
(holds with a correction), REFUTED (does not hold).

Note on line numbers: the spec cites `auto_tick.py:373` and
`auto_tick.py:386` and `events.py:112-118`. Those files on disk are
121 and 60 lines. The cites do not match the files; the substance
behind them was verified and holds. Do not forward those numbers.

## 1. Out-of-order turns on the Bryan-approved path — CONFIRMED

`sweep.validate()` rejects only older turns (`STALE_PROPOSAL` error when
turn < last_swept) and flags an equal turn (`TURN_ORDER`, flag only).
There is no forward-gap check. Only `auto_apply.check_eligible`
enforces "next turn", and only on the auto path. A Bryan-approved
apply of Turn 145 when 138 was last swept passes validation and
applies, setting last_swept_turn to 145. Turns 3 and 4 queued behind
Turn 2 are held only by process, not by code.

## 2. Lore approval is unverified — CONFIRMED

`proposals.apply_proposal` checks `approved_by != "Bryan"` (a string
compare) and records `lore_approval` in the binding without ever
reading `lore-approved.json` or the registry entry's `lore_approved`
flag. `record_lore_approval` writes both, but nothing reads them back
at apply time. A `lore_approval` value that was never issued applies
exactly like one that was.

## 3. Registry races and DB-then-registry non-atomicity — CONFIRMED

`apply_proposal` loads the registry at the start and saves it at the
end as a stale snapshot; `intake_folder` does the same. A poll
registration landing in between is clobbered. The DB commits inside
`apply_sweep` before the registry entry is marked `applied`: a crash
in between leaves the DB applied and the registry still `reviewed`,
and a re-apply would pass (turn == last_swept is only a
`TURN_ORDER` flag) and append duplicate sweep events with the same
values.

## 4. Check-then-write and append_event races — CONFIRMED (mechanism); reachability caveat

`apply_sweep` computes `diff()` outside the `with conn:` transaction
and writes absolute `UPDATE ... SET value = ?` inside it. A tick
landing in between gets overwritten. `events.append_event` reads the
last hash (`last_hash`) then inserts, with no transaction guard;
`db.connect` uses default deferred isolation and there is no
`BEGIN IMMEDIATE` anywhere. A second writer can fork the chain and
`verify_chain` then reports it as tampering.
Caveat: today there is effectively one DB writer. Intake never writes
the DB and the daily auto-tick cron is disabled, so the DB fork is
latent; the registry clobber in item 3 is the live race. The DB fork
becomes realistic the moment the daily cron returns or a second
writer appears.

## 5. Three RNG regimes — CONFIRMED, corrected to two schemes over three drivers

- Manual / turn-driven: `run.py cmd_tick` creates
  `random.Random(rng_seed)` per invocation, and `attempt_auto_apply`
  calls `run_ticks(conn, 3)` with no rng, so `run_ticks` re-seeds from
  `rng_seed` on every call. Each CLI invocation replays the same
  random sequence from the start.
- Auto: `auto_tick` seeds `random.Random(seed + tick)` per tick.
- `seed + tick` collides: seed 5 at tick 3 equals seed 3 at tick 5.
  Hash the tuple instead.
Weights: 24 of the 25 Fork A actions have weight 5 (`rest` is weight
0), so score ties are the norm and the RNG tie-break is the main
decision-maker. Chunked ticking differs from continuous ticking.

## 6. Halt commits a partial tick; the daily guard is not set — CONFIRMED

`run_ticks` advances the tick number first, then on `EngineHalt`
appends a halt event, commits the partial tick, and raises. Actors
that had not acted yet are skipped and a resumed run never replays
them. `auto_tick`'s halt branch returns without setting
`last_auto_tick_date`, so a retry ticks again — a new tick each time,
re-running the earlier actors and halting again if the condition
persists. Each retry consumes another partial tick.

## 7. Silent success on missing targets — CONFIRMED

`status_set`, `move`, `molt_trigger_set` return success-shaped ops
when the id does not exist (the UPDATE touches 0 rows; the returned
op carries `old_status`/`old_location` None and no marker).
`standing_set` has the same shape and was not listed. Contrast
`clock_add` / `bond_add` / `hunger_add` / `hunger_set`
(`applied_qty: 0`) and `location_set` (`applied: []`), which do
signal that nothing happened.

## 8. Raids use independent resource_add, not resource_move — CONFIRMED + quantified

Both forks' raid actions are two separate `resource_add` ops: Feed -2
from the victim, Salvage +2 to the raider. Different resources, so
not a transfer even when the raid lands. Over 1,000 ticks:
1,996 raids fired, 2 landed (ticks 1 and 3), 1,994 blocked, 0 Salvage
created from nothing observed — both landed raids had full Feed
available, so the clamp never engaged. The creation path is
structural (independent ops, no coupling between the take and the
grant) but unexercised in this run, because fortification at tick 3
blocks every later raid.

## 9. last_auto_tick_date leaks wall-clock into state_hash — CONFIRMED

`STATE_TABLES` includes `meta`, and `state_hash` hashes every meta
row. `last_auto_tick_date` is a meta key set by `auto_tick`, so two
identical worlds differing only in that date hash differently. This
contradicts the comment at `db.py:10-11` (deterministic fields only)
and breaks any golden-hash test run on different days.

## 10. Fork A freeze is only the literal pair — CONFIRMED

The only freeze enforcement is `sweep.py` `FROZEN_TURN = 136` /
`FROZEN_VERSION = "vFINAL.5"` in `validate()` (turn == 136 AND
version == vFINAL.5 → error). A grep of `src/` and `seed/` finds no
fork-level frozen flag. `checkpoint.py`'s frozen-terms scan is a
different mechanism: it reports events mentioning frozen terms
(krov, motherbulwark, ...) and does not block. Note the pair check
also lets a Turn 136 block with a different version through.

## 11. Patrol never blocks raids — CONFIRMED, with an event trace

Double lock in the code: tick flags are cleared at tick start
(`DELETE FROM tick_flags WHERE tick < ?`), and NPCs act in
`ORDER BY id`, so raiders (`breaker_poacher_chief`,
`dust_baron_captain`) always act before patrollers
(`legion_captain`, `tull`). Evidence over 1,000 ticks: 568 patrol
events; 491 ticks where a raid and a patrol both fired, and in all
491 the raid event id is lower (earlier) than the patrol event id;
applied "raid blocked: Great Basin patrolled" notes: 0 of 1,996
raids. The applied blocked note is always the fortified one (1,994).
Patrol is pure theater.

## 12. Dead seed content — CONFIRMED

- `concord_blockade` and `legion_cohesion` have zero `clock_add`
  sources in the 25-action catalog (only `great_basin_recovery` ×2
  actions and `dust_baron_retaliation` ×1). They sit at 0/6 forever.
- Territory and Cores: no effect op in either seed touches them.
  Simulation confirms zero changes over 1,000 ticks.
- `raid_in_progress:concord_camp` is never set (only the
  `great_basin` variant is, by the two raid actions). `evacuate`
  (trigger: that flag) fired 0 times and is unreachable; even if the
  flag were set, `evacuate` halts asking Lore instead of acting.
  `pack_merge`'s `concord_camp` disjunct is likewise unreachable;
  its other two disjuncts are live.
- Display wart found on the way: `leviathans_ribs` and
  `northern_trench` get mapped and claimed but keep the status
  string "unmapped" — the reveal op sets `mapped = 1`, never the
  status.

## 13. Clocks are one-shot; Great Basin stays fortified; exhaustion tick — CONFIRMED

`clocks.check_completions` fires once per clock (status running →
complete) and there is no reset path anywhere. No action un-fortifies:
only the recovery clock's `on_complete` sets `fortified`. Over
1,000 ticks the Fork A world runs out of significant events at
**tick 26** (the last significant event, the fifth and final engine
repair). Structural change ends earlier, at **tick 3** (last clock
advance, last clock completion, last controller change, last raid
gain, last claim). After tick 26 the world is routine economy and
no-op churn.

## 14. Skipped ops — CORRECTED in part

`render.py` (`_effect_text`) and `handshake.py`
(`_off_screen_lines`) both correctly ignore skipped ops — a skipped
op renders as nothing. The README tick 399 row is the misleading
one: it is hand-written (or rendered from raw effect JSON without
the filter). Real events do contain applied gains beside a skipped
"raid blocked" note — exactly 2 such events in the runs, the two
landed raids at ticks 1 and 3, where both blocked-notes are skipped.
The README prints the skipped note text as if it happened.
Rumors: a false positive is real. `_rumor_for_event` does not check
whether the raid's resource ops applied; it takes the place from any
op value, and the raid's `flag_set` (no `when`, always fires)
supplies "great_basin". A fully blocked raid (all gains skipped,
blocked note applied) still yields "Rumor (unverified): word from
the road says raiders struck near Great Basin."

## 15. Target selectors can hit the player's engine — CONFIRMED

`engine_at_location` takes any engine at the location (no faction or
player filter); `lowest_bond_engine` takes the lowest-Bond living
engine below max. Fork B has exactly one engine, so
`lowest_bond_engine` always returns Ashfang. Fork B actions that can
change Ashfang's state:
- `net_ambush` (`breaker_poacher_chief`, `engine_at_location` →
  status `netted`). Already fired once (tick 3). The only
  non-story-owned action that can change his status.
- `repair_engine` (`pike`, status → `field-patched`).
- `dream_share` (`rin`, `lowest_bond_engine` → Bond +1).
- `hunt` and `feed_engine` (`rin`, `pike`, `nest_keeper`;
  `engine_at_location` → Hunger -2). The Nest-Keeper's copies can
  hit Ashfang if co-located.
- `pack_merge` does NOT exist in Fork B (the spec's candidate list
  needs that correction).
Plus core tick paths, not actions: Hunger +1 every tick for every
living engine (step 2), and Instinct (step 3: hunger at threshold →
Feed +2, Hunger set to 4). Under Step 3, `net_ambush` is the hook
case; Rin's and Pike's actions leave the tick with `story_owned`.

## 17. (Step 4B) Actions that can fire only once in the world's lifetime

"Fire" here means have an effect, not merely be chosen: several
actions keep being chosen as no-ops after their effect is spent.
- Clock completions: once per clock (4 max; 1 achievable as seeded).
- `scout_wreck` and `dream_share`'s reveal branch: bounded by the 2
  unmapped locations (shared pool). Each reveal consumes one.
- `claim_*`: once per location. 7 locations; the 3 that were
  claimable were all claimed by tick 3.
- `bargain`: High Baron's status chain (under guard → watched →
  active), 2 transitions total, fired twice.
- `fortify`'s clock effect: once (drives recovery to 6). The action
  keeps firing afterward (454 times in 1,000 ticks) and each firing
  burns 1 Salvage for nothing — a resource sink, not just a no-op.
  (`need` is a scoring bonus only, not a legality gate, so nothing
  stops it being chosen.)
- `repair_engine`'s clock effect: same clock, same once-only effect.
  Its status effect recurs only if engines re-enter repairable
  states. The seed starts all 5 engines exhausted; Vance repairs
  all 5 by tick 26; nothing in Fork A re-exhausts them.
- `raid_captain`'s clock effect: bounded by retaliation 6/6 (stuck
  at 1/6).
- `evacuate`: zero times, structurally unreachable (item 12).
- `net_ambush`: zero times in Fork A — the chief sits at
  Chalk Canyons, the engines at Great Basin, and nothing moves
  either of them. Live in Fork B, where chief and Ashfang share the
  Rust Dunes.
- `scavenge_dust_baron` / `scavenge_breakers`: zero times, two
  different deadlocks. Breakers: the sibling raid's `need` bonus
  (+1 while Salvage < 3) outscores scavenge 6 > 5 every tick, and
  Salvage stays at 2 because raids never land. Dust-Baron: the
  trigger itself fails — Salvage hit 5 at tick 3 (the one landed
  raid) and never moves again, so `Salvage < 4` never holds.
- NOT once-only: `legacy` (periodic per era); `pack_merge` /
  `dream_share` / `fortify` as chosen actions (they keep firing;
  only their story effects are finite).

## Step 4B record (audit first — nothing here is built)

Problem: the catalog is finite and nothing renews it. Clocks
complete once and stay complete, the two unmapped locations run
out, and once Great Basin is fortified the raid storyline ends
permanently. After that the world only scavenges, claims, and
rests. Measured above: significant events hit zero in the 101-200
window and never recover.
Rules: the engine only chooses among pre-approved content, never
invents canon; new content arrives as Lore-approved seed packs;
everything deterministic on the Step 2 per-actor RNG streams; any
effect touching a story-owned actor becomes a hook (Step 3), not an
applied change; seed changes are proposed as diffs; Fork A's seed
is never modified.
Build order (each needs a plan and test list first): A. repeatable
clocks (`repeat` field, tiered on_complete); B. entropy (fortified
expiry, standings drift); C. wake the dead clocks (real sources
driven by world conditions); D. stagnation meter with a
Lore-approved disruption pool, scaled by distance from the player;
E. pressure-driven goals (conditions, not actor whitelists);
F. mortality and succession (ages, death rules, `npcs.successor`);
G. era turnover (seed packs retire/add content, activate dormant
factions like Rust Choir); H. frontier pool (seed-defined locations
appearing as scouting continues).
Balance simulator addition: report significant events per 100
ticks; fail a seed if the rate drops to zero before tick 1,000.
Fork A as seeded FAILS this test (zero from the 101-200 window).
Acceptance: a 2,000-tick run on the revised Fork B seed keeps
producing significant events throughout, passes
`verify_invariants`, is deterministic across repeat runs, and
leaves all 151 existing tests passing.

## Appendix: the `turn` one-command wrapper — Step 0 audit (no code)

### 1. Existing commands and what the wrapper reuses

`src/run.py` subcommands: `seed`, `tick`, `fast-forward` (alias of
`tick`), `render`, `verify`, `sweep`, `handshake`, `intake`,
`apply-proposal`, `checkpoint`, `auto-tick`.
The wrapper chains steps the engine already has:
- Read block: `cmd_sweep` already reads a local block file
  (`--block`); stdin is new.
- Parse: `sweep.parse_state_block`.
- Validate: `sweep.validate` + `proposals.validate_fork`.
- Diff: `sweep.diff`.
- Routing tiers: `auto_apply.check_eligible` (turn/version/base/
  pending/session) + `auto_apply.flag_narrative_changes`
  (narrative flags). AUTO/REVIEW/HOLD map onto these, plus the new
  hard turn-order gate (below).
- Session flag: `session.is_open` / `refuse_reason`.
- Apply: `sweep.apply_sweep` in one transaction (the same call
  `cmd_sweep --apply` and `apply_proposal` both make).
- Tick 3: `tick.run_ticks` (see 2).
- Handshake: `handshake.generate_handshake` + the sweep records
  writer `_write_sweep_records` (applied.json + carried.json +
  review.json under `runs/sweeps/turn-<n>/`).

### 2. How the 3-tick advance after apply is invoked, and which RNG

`attempt_auto_apply` (the intake auto-apply path) calls
`tick_mod.run_ticks(conn, ticks)` with `ticks = 3` and no `rng`
argument, so `run_ticks` re-seeds `random.Random(rng_seed)` on the
call. `cmd_tick` does the same thing explicitly
(`rng = random.Random(int(db.get_meta(conn, "rng_seed", 0)))`).
The wrapper must call `run_ticks(conn, 3)` with no rng argument —
identical semantics, no tick change. Keep the rest of that path
too: `attempt_auto_apply` runs `verify_invariants` and
`verify_chain` after the tick and refuses the handshake on problems
or a halt; on a halt the apply stands, no handshake is generated,
and the record says so loudly. The wrapper spec's step 9 (halt →
report and stop, no retry) matches this; the spec should also keep
the invariants/chain checks, which it does not currently mention.

### 3. Can apply_proposal run from a local file without Drive? No — an adapter is needed

`proposals.apply_proposal(pid, conn, approved_by, ...)` requires a
registry entry with status `reviewed`, re-downloads the Drive file
by `entry["drive_file_id"]`, hash-compares it, then applies the
stored `proposal.txt`. A local file has no Drive id and no registry
entry, so it cannot run as written. The adapter is small and keeps
every safeguard:
- Register the local block as a proposal in the fork's registry
  (proposal.txt + review.json + registry entry with proposal id
  `prop-<turn>-<hash>`, content hash, source `local-file`,
  `drive_file_id` None), scoped by `IRONWILD_PROPOSALS_DIR` to the
  fork's proposals dir exactly as the intake cron does.
- At apply time, re-read the local file and hash-compare against
  the registered hash — the same binding as the Drive re-download,
  with the local file in place of Drive.
- Apply through the same `apply_sweep` in one transaction; record
  the binding (approver "Bryan", source `local-file`, content hash,
  timestamp) in applied.json, exactly as `apply_proposal` does.
- Session-flag check and validation-error refusal stay (both are
  enforced inside `apply_sweep`).
- Idempotency comes free from the registry: content-hash dedupe on
  intake plus `apply_proposal`'s refusal of any entry whose status
  is not `reviewed` (a second run finds status `applied` and
  refuses with "already applied").
- The turn-order gate (turn must be exactly last_swept_turn + 1,
  an error on every path including human approval) is NEW.
  `validate()` does not enforce it (audit item 1). Implement it as
  a wrapper-level gate before apply, not as a change to
  `validate()`, which would alter intake/review behavior on all
  paths.
- Backup (`.backup` to `runs/backups/<fork>-turn-<n>-pre.sqlite`)
  and rollback are new — no backup code exists. Recommend
  `sqlite3.Connection.backup()` (a consistent snapshot) over a raw
  file copy. Rollback restores the most recent pre-apply backup
  after confirmation.
- `--queue` needs a defined source: the registry (statuses
  `reviewed`/`held`, ordered by turn) covers proposals; "files
  waiting" needs a local queue directory convention, which the spec
  does not define — open design question for the build plan.
- No schema change is strictly needed for the wrapper. The Step 1
  `applied_turns` table would strengthen idempotency but the
  registry already provides it; note as optional, not required.
- State-hash equivalence: the wrapper calls the same functions in
  the same order, so hashes match the current pipeline for the same
  input provided the RNG path is identical (no-rng `run_ticks`) and
  the adapter writes nothing extra to the DB (registry and backup
  are files, not DB writes). One caveat: the adapter must parse the
  stored file at apply time, not the stdin buffer, matching
  `apply_proposal`'s stored-content rule.
- Pre-existing wart the wrapper should not worsen: sweep records
  live in the shared `runs/sweeps/turn-<n>/` namespace across
  forks. Fork A and Fork B will eventually collide on a turn
  number there. The wrapper's handshake path
  (`runs/<fork>/handshakes/turn-<n+1>.txt`) is correctly per-fork;
  the sweep records are not.
- Scope note: the wrapper handles the mechanical path. Lore/Bryan
  decisions still happen in chat/the hub before the wrapper runs —
  it does not replace Lore routing. For the acceptance case (Fork B
  Turns 2, 3, 4 in order), Turn 2's hatch decision must be resolved
  first, and Turns 3 and 4 need their revised blocks (Bond 2/5)
  before the wrapper can take them as input.
